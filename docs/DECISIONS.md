# Decision log

Dated, short. Each entry says what was decided, why, and what it costs.

## 2026-11-26

**Track 1, Policy administration.** One product line (commercial liability for startups), three coverages from a small catalog (General Liability core; Cyber and Tech E&O add-ons). Chosen because the brief's test (correct a back-dated effective date and explain the new amount) is a ledger problem, and I wanted the whole build to serve that.

**Append-only ledger; the balance is derived.** `ledger_entries` rows are never updated or deleted. Amount due is `SUM(amount_cents)`, not a stored number. Corrections add rows. This is what lets the customer see the original charge and the correction as separate lines, and what lets any amount be traced to the action behind it (`action_id`). Cost: reads do an aggregate; fine at this scale, and indexed by `policy_id`.

**`reconcile()` makes the ledger match the policy "as it is now".** After any action (issue, add coverage, correct date, cancel) it recomputes the expected premium per coverage from the *current* effective date and appends the difference against what is already booked. One code path covers charges, corrections and cancellation credits, so they cannot disagree with each other. Cost: it recomputes every coverage each time; trivial with a handful of coverages.

**Two dates per coverage change (bitemporal).** `effective_date` is when cover applies; `recorded_at` is when we learned it. A correction inserts a new `CoverageVersion` and flips the old one to not-current; nothing is overwritten. The broker UI shows the superseded date struck through; the customer sees a banner explaining what changed and why.

**Money is integer cents; dates are DATE, not datetimes.** No floats. No timezone arithmetic on coverage days.

**Pricing.** Catalog gives an annual (365-day) price per coverage and limit. A coverage's full-term premium is `annual × term_days / 365`. A coverage that starts mid-term is charged `term_premium × covered_days / term_days`, rounded half-up to the cent once per coverage (not per day). Covered days = `end − effective`, where the term end date is exclusive ("expires on", first day not covered). Worked example in README.

**Cancellation rule.** Pro-rata, effective 00:00 on the chosen date, unearned premium refunded to the original payment method(s); no short-rate penalty, no fee. A cancellation date on the start date is a flat cancel (full refund). Cancellation before an add-on's effective date earns nothing for that add-on. Alternative I did not build: short-rate (e.g. 90% of pro-rata) which insurers often use.

**Negative corrections create a credit, not an automatic refund.** If a correction moves a date *later*, the customer is owed money. The ledger balance goes negative ("credit on account") and the broker decides whether to refund it ("Refund credit"). On cancellation the refund is automatic because intent is clear.

**Refund amount is capped by cash actually received.** Refund = min(credit, paid − already refunded). If the customer never paid, a cancellation credit just reduces what they owe. Unpaid corrections net off against refunds (e.g. $70 unpaid reduces the refund by $70).

**Payments are state machines driven by one event handler.** `apply_provider_event()` is the only place payment/refund outcomes change state. Stripe's signed webhook and the simulated confirmation both call it, so the simulated path exercises the same code. Idempotent on provider event id; a payment already `succeeded` can't be double-booked by a second event. A payment may go `failed → succeeded` (Stripe lets a customer retry the same PaymentIntent).

**Payment attempts don't touch the ledger until they succeed.** Pending/failed attempts are shown separately on the statement ("Payment attempts not on the statement"). Only a succeeded payment appends a `PAYMENT` entry. If the amount due changes while a payment is pending, the old attempt is marked `canceled` and a new one is created; if the old one still succeeds later it is still booked (we took the money), and the balance shows the difference.

**Two integrations.** Stripe (PaymentIntents + Refunds + signed webhooks, test mode only; the provider refuses non-`sk_test_` keys) and Resend (transactional email). Each sits behind a small interface with a simulated implementation, so the app runs offline and the README states which mode is active. The UI shows LIVE vs SIMULATED badges everywhere it matters.

**Auth is deliberately minimal.** Seeded demo users, PBKDF2 password hashes, JWT bearer tokens, role checks on every route, customers can only read their own policies. No password reset, no MFA, no invites (broker sees a temporary password once). Called out as a simplification.

**No Alembic migrations (yet).** Schema is created with `create_all` on startup. Fine for a throwaway demo database; the first thing I would add for a real deployment.

**SQLite in dev, Postgres in prod.** Same SQLAlchemy code; the whole test suite runs against both (SQLite in-memory, and a real Postgres 16 locally and in CI).

**UI.** Design tokens read from corgi.insure (orange #ff5c00, ink #1d1d1d, canvas #f6f6f6, 0.5rem radius, Geist, italic serif accent). Original wordmark and icons only; no Corgi logos or mascot artwork. Every statement line expands to show the formula and the action/actor/reason behind it ("explain this amount"). Broker actions show a live preview of the amount *before* confirming.

**Repo and delivery.** Private GitHub repo `zivgura/corgi-work-trial`, `main` branch, three commits (backend, frontend/e2e/infra/docs, flaky-test fix). Pushed over SSH after HTTPS pushes of larger commits were cut off by the network; no code change was needed.

**Decision log is a living document.** Every meaningful choice from here on (hosting, live-integration findings, bugs found in verification) gets a dated entry in this file in the same change that makes it.

**Stripe integration: restricted test key, webhook via CLI locally.** Stripe account is a Sandbox (test environment). The backend uses a restricted `rk_test_` key created for this project (least privilege: no payouts or card issuing); the provider code refuses any key that is not a test key. Locally, the Stripe CLI forwards signed events to `/api/webhooks/stripe` and supplies the `whsec_` signing secret; in the deployed app a dashboard webhook endpoint replaces it. Keys live only in the git-ignored `backend/.env`, never in the repo or chat logs. Cost: the CLI must be running for local payments to reach the ledger; the deployed endpoint removes that dependency.

**Bug found in first live Stripe test: reused payment attempt had no client secret.** The Stripe PaymentIntent client secret is intentionally not stored (it is a credential for the browser). `create_payment` reuses an open attempt for idempotency, but that path returned it without a secret, so the card form could not render and the customer was stuck on "Payment pending". Fix: when reusing an attempt, re-fetch the secret from the provider (`client_secret_for`); an attempt created under a different provider mode (simulated vs Stripe) is cancelled instead of reused. Two regression tests added. Why it escaped earlier tests: the simulated provider has no card form, so only the real Stripe path exposed it, which is the value of the live integration check.

**Payment UX: lock the page while paying; a failure ends the attempt.** While a payment is being created or confirmed, everything outside the pay card (header, nav, coverage, statement) is dimmed and made `inert`, and leaving the page asks for confirmation, so a customer cannot navigate away or double-act and be unsure whether they were charged. The Pay button stays disabled until Stripe reports every card field complete and valid; form mistakes are shown to the customer and never reach the bank. A declined card ends that attempt with a clear "you have not been charged" message and "Try again" starts a fresh attempt, rather than retrying the same PaymentIntent: the status poll cannot tell an old failure from a new one on a re-confirmed intent, so a fresh attempt is the unambiguous design. If the bank is still confirming after ~20s the customer is told it is safe to leave and not to pay again, and the policy page keeps polling until the webhook lands. Cost: each retry leaves a failed attempt in the "attempts not on the statement" list, which is accurate history.

**All errors are toasts, caught in one place.** Errors never render inside the component that caused them. A single toast stack (top-right, auto-dismiss, light theme) receives: failed queries and mutations (react-query cache hooks), explicit `ErrorNote` calls, uncaught exceptions, unhandled promise rejections, and React render crashes (an error boundary also shows a reload fallback so the page is never blank). Transport errors such as a proxy's plain-text "Bad Gateway" are translated to "We couldn't reach the server. Please try again in a moment."; messages the backend wrote deliberately (e.g. "Nothing is due on this policy") are shown verbatim. Identical toasts are de-duplicated while visible. Stripe's own field-validation messages stay inline next to the field, since they say which field to fix. Covered by Playwright tests (rejected login, simulated 502, network abort, uncaught rejection). Cost: a toast disappears after a few seconds, so a customer who looks away can miss it; errors that block a page (cannot load) therefore also leave a persistent "We couldn't load this page" placeholder.

**Webhook is the primary path, but the app reconciles with Stripe so a lost event cannot cause a double payment.** Found in live testing: Stripe recorded `payment_intent.succeeded` for $2,400.00, but our app never received the webhook (local forwarder not delivering), so the policy stayed "pending" and the customer was offered to pay the same amount again. Fix: whenever a policy has an open attempt, the backend asks Stripe for the PaymentIntent's real status (`sync_pending_payments`, run when the policy, its statement or its payments are read, and before a new attempt is created) and books the outcome through the same idempotent handler the webhook uses (event ids `sync_<pi>_<outcome>`, tagged `source: reconciliation` as honest evidence). A webhook arriving later is a no-op, so the payment is booked exactly once. A cancelled PaymentIntent marks the attempt cancelled; a declined one marks it failed with Stripe's reason. Also: an unfinished attempt now reads "Continue payment" with a plain explanation instead of a second "Pay" button, and the card form reports load failures as a toast (it was failing silently). Cost: one Stripe API read per poll while an attempt is open (every 3s on the policy page); acceptable here, and the webhook remains the source of truth in normal operation. Three tests cover lost webhook then late webhook, no second offer on a paid policy, and failed/cancelled outcomes.

**Bug found by reading the forwarder log: the webhook handler returned 500 for every handled event.** The Stripe CLI showed our endpoint answering `[500]` to `payment_intent.succeeded`, `refund.created`, `charge.refunded` and `refund.updated` while the unhandled `charge.refund.updated` got `[200]`. Cause: the handler passed `dict(event)` to the database, but current stripe-python event objects are not dicts (`TypeError: Event is not iterable or a mapping`). Why it escaped: no test posted a real signed event to the route (the earlier suite used the simulated path), and the reconciliation fallback, added the same day, was masking it by booking payments on read. Fix: verify the signature with Stripe's library, then read the verified body as plain JSON. A test now signs real-shaped events (payment success, a repeat delivery, and the three refund event types) and posts them to the route; a second test checks that a bad signature is rejected with 400. Lesson recorded for the debrief: a fallback that works can hide a primary path that does not, so the Integrations page labels reconciled events (`sync_` ids) separately from real webhook deliveries.

**Bug found in live verification: one Stripe payment was booked twice.** On policy CRG-000004 the signed webhook (`evt_…`) and the reconciliation poll (`sync_…`) handled the same PaymentIntent 130 ms apart; each read the payment as `pending` before the other committed, so the ledger got two PAYMENT entries (Paid $3,600 on a $1,800 charge) and two emails. The old check-then-set on `pay.status` was not atomic. Fix: `_claim_payment()` does the transition as one `UPDATE payments SET status=… WHERE id=? AND status NOT IN (…)`; only the caller that changes a row books the ledger entry and sends the email, the other gets "duplicate". Works on SQLite and Postgres without row locks. Regression test applies the two events from two sessions with a stale read, and fails (`applied, applied`) against the old code. Policy 4 in the local DB holds the corrupted test data and is not used for the demo.

**Resend is live (sandbox sender), limited to one recipient.** A sending-only API key (`corgi-work-trial`, not full access) is in `backend/.env`, never in git. Without a verified domain Resend's test sender `onboarding@resend.dev` only delivers to the account owner's address, so the live demo customer ("Ziv Test Co") uses that address; older demo customers keep simulated-looking addresses and would be rejected by Resend. First live send: "Your Corgi policy CRG-000006 is ready", status `sent` in our email log with Resend message id, `Delivered` in Resend's own log. Email failures never block money movement (the ledger commits first; a failed send is logged with its error). For a real deployment: verify a domain and send from it.

**Emails are branded HTML with a plain-text fallback.** The plain-text body stays the source of truth (it is what we log and show on the Integrations page); `email_html.py` wraps it in the app's design tokens (orange #ff5c00, ink, canvas, a status badge per email type, "Open your portal" button to `APP_URL`). Inline CSS and table layout because email clients ignore web fonts and external stylesheets, so Geist/Instrument Serif fall back to system fonts there. All dynamic text is HTML-escaped. Only the Resend path sends the HTML part; simulated mode just logs.

**Email redirect in the Resend sandbox.** Resend's test sender delivers only to the account owner, but demo customers (e.g. the seeded `ada@acme-ai.test`) have other addresses, so every send to them would fail and look like a bug. `EMAIL_REDIRECT_TO` (unset by default) delivers every email to one address instead, with `[to <real recipient>]` in the subject and a banner in the body. The app's own email log still records the real recipient and the original subject. With a verified domain this setting is simply left empty.

**Hosting: Render, free tier, one Docker service (API + built SPA) plus free Postgres.** Chosen because `render.yaml` describes the whole stack, so the reviewer-facing URL is reproducible from the repo. Free instances sleep after inactivity (about 50 s cold start) and free Postgres expires after 30 days; the alternative was about $13/month always-on. Because a sleeping service can miss a Stripe webhook, the app also asks Stripe for the status of any open payment whenever the policy is loaded (see reconciliation above), so no payment can stay unbooked. Secrets (Stripe keys, webhook secret, Resend key) are `sync: false` in the blueprint and live only in Render's dashboard, never in git. The webhook endpoint is registered in the Stripe sandbox against the deployed URL (events: payment_intent.succeeded, payment_intent.payment_failed, charge.refunded, snapshot payloads).

**Card payments only, configured in Stripe, not in code.** The first live PaymentIntents offered Bank, WeChat Pay and Klarna, none of which is a requirement or suits a commercial premium (slow-settling debits add failure states we do not model). First attempt: `payment_method_types=["card"]` in code. Found in production verification that Stripe API version 2026-11-18 rejects that parameter ("Payment methods are now managed from Dashboard settings"), so the code is back to `automatic_payment_methods` (redirect-based methods disabled) and the allowed methods are switched off in the Stripe sandbox's payment-method settings. Adding ACH later would mean handling `processing` as a payment state.

**Bug found in live verification: refund idempotency key collided across databases.** First live refund (CRG-000002, $1,795.07) was rejected by Stripe with "Keys for idempotent requests can only be used with the same parameters they were first used with". The key was `refund-<local refund row id>`; my local dev database and the deployed database share one Stripe sandbox account, and both had a refund row with id 2. The app handled it correctly (error toast, ledger credit untouched, nothing booked as refunded), but the key was not unique. Fix: the key is now `refund-<PaymentIntent id>-<refund row id>`. It is still deterministic for a retry of the same refund row (so a network retry cannot double-refund) and unique across databases because PaymentIntent ids are. In production there is one database, so this only bit because demo and dev share a sandbox.

## Not built (on purpose)
Claims, renewals, broker commissions, endorsements other than adding coverage / correcting its start date, premium taxes/fees, multi-currency, installment plans, document (COI) generation, password reset/MFA, concurrency control beyond DB transactions (two brokers editing one policy at the same instant could interleave; a row lock on the policy in `reconcile` is the fix).
